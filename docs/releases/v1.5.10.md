# Release v1.5.10

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-abb-fimer-pvi-vsn-rest/v1.5.10/total?style=for-the-badge)](https://github.com/alexdelprete/ha-abb-fimer-pvi-vsn-rest/releases/tag/v1.5.10)

**Release Date:** 2026-08-10

**Type:** Patch release — VSN300 firmware 2.0.x support (authentication + charset), firmware
2.0.0 guard, and re-discovery fixes for zero-sensor startups.

## What's Changed

### Added

- **Guard for unsupported VSN300 firmware 2.0.0** (Reported in #68) — VSN300 datalogger
  firmware 2.0.0 has a vendor bug: the `/v1/livedata` endpoint drops every TCP connection,
  making the integration inoperable. The vendor fixed it in firmware 2.0.1, so the
  integration does not carry a workaround for 2.0.0; instead it now detects this exact
  condition (VSN300 + livedata connection failure + `fw.release_number` 2.0.0) and guides
  the user to the fix:

  - **First-time setup**: the config flow shows a clear "unsupported firmware, upgrade
    to 2.0.1" error instead of a generic connection failure.
  - **Existing installation**: setup raises a repair issue with upgrade instructions and
    fails with a non-retrying setup error. The repair issue clears automatically once the
    integration starts successfully after the upgrade.

- **VSN300 firmware 2.0.0/2.0.1 reference samples** — Raw API captures (status, config,
  bare feeds, per-device datastreams, and raw livedata socket transcripts) from both
  firmware versions, contributed by @gseguin, added to `docs/vsn-data/vsn300-data/`. The
  transcripts document the 2.0.0 regression (0-byte connection close) and the 2.0.1 fix.

### Fixed

- **VSN300 X-Digest authentication aligned with the firmware's own web UI constants**
  (Reported in #68, contributed by @gseguin in PR #69) — The digest header now sends the
  exact `nc=00000002` / `cnonce=ddf4bfcaf87acba9` values that the VSN300 firmware's own
  web UI (`auth-filter.js`) uses. Every firmware build must accept its own web UI's
  headers, so the constants are the maximally compatible choice — verified on fw 1.9.2,
  2.0.0, and 2.0.1 hardware.

  *Post-release correction (2026-08-10):* the original report attributed hard 401
  failures to the previous random nc/cnonce; follow-up testing on the same hardware
  could not reproduce them — stock RFC-style values are also accepted on all firmware
  tested to date. The constants are kept as a robustness/alignment fix: they carry a
  structural acceptance guarantee, while random values are the only configuration ever
  reported failing in the field.
- **Non-UTF-8 JSON responses crashed discovery** (Reported in #68, fixed by @gseguin in
  PR #69) — The datalogger can serve ISO-8859-1 bodies (e.g. accented characters in
  user-entered device/plant labels) while the `Content-Type` header claims UTF-8 or omits
  the charset, crashing `response.json()` with `UnicodeDecodeError`. A new shared
  `read_json_lenient()` helper reads the raw bytes, tries UTF-8 first (byte-identical for
  all ASCII payloads), and falls back to latin-1 on decode error; all client, discovery,
  and auth call sites route through it.

  *Post-release verification (2026-08-10):* a hardware capture with an accented plant
  name confirmed the firmware stores current user-entered text as genuine UTF-8
  (`é` → `0xC3 0xA9`), validating the UTF-8-first order — a forced latin-1 decode would
  have rendered it as mojibake.
- **Automatic re-discovery never ran when setup created zero sensors** — If Home Assistant
  (re)started while the datalogger returned an empty `/v1/livedata` response (typical when
  HA boots before sunrise, or right after a datalogger reboot), sensor setup created 0
  entities. Home Assistant's `DataUpdateCoordinator` only schedules refreshes while it has
  listeners, and the integration's only listeners were the sensor entities — so with zero
  sensors the coordinator never polled again after the first refresh. As a result
  `_attempt_rediscovery()` never ran, the "Incomplete device discovery" repair issue never
  cleared, and the integration stayed stuck (all entities `Unavailable`) until a manual
  reload — contradicting the repair notification's promise to re-discover devices
  automatically. The integration now registers a no-op coordinator listener during setup so
  polling (and therefore re-discovery) continues even when no entities exist. A regression
  test asserts the listener is registered and released on unload.
- **Devices already known and discovered never got their entities back after their livedata
  returned** — Companion gap to the fix above: a device that is present in discovery but
  absent from livedata at setup got zero sensors, and no existing check could recover it.
  This is systematic for the VSN300 datalogger: it is synthesized from `/v1/status`, so it
  is never "missing" from discovery (which is what triggers the missing-device
  re-discovery), and it is already in `known_devices` (so the unknown-device idempotency
  check never fires). Observed in the field when a VSN300 rebooted with an unsynced clock
  and stopped publishing its own entry in `/v1/livedata` — its 16 diagnostic sensors stayed
  `Unavailable` even after the data returned. The coordinator now runs a third check each
  poll cycle: the sensor platform records which devices actually got entities, and when a
  device starts reporting points without having any, a reload is scheduled to create them.
  The check is skipped until the sensor platform has completed setup, and point-less device
  entries are ignored to prevent reload loops (e.g. the VSN700 datalogger, whose livedata
  entry legitimately has an empty points array).
