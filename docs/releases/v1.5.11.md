# Release v1.5.11

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-abb-fimer-pvi-vsn-rest/v1.5.11/total?style=for-the-badge)](https://github.com/alexdelprete/ha-abb-fimer-pvi-vsn-rest/releases/tag/v1.5.11)

**Release Date:** Unreleased

**Type:** Patch release — work in progress.

## What's Changed

### Added

- **Genuine-UTF-8 regression fixture for the charset-tolerant decoder** (Refs #68,
  contributed by @gseguin in PR #73) — A real fw 2.0.1 `/v1/config` capture with an
  accented plant name stored as two-byte UTF-8, plus a regression test pinning
  `read_json_lenient()`'s UTF-8-first decode order against the real payload.

- **Repair issue for a datalogger that stops reporting its own data** — The VSN300
  datalogger can keep serving the REST API (polls succeed, inverter data flows) while
  omitting its own device section from `/v1/livedata` — observed on fw 1.9.2 after a
  reboot without clock sync (NTP unreachable): its sensors go unavailable with no
  explanation, and none of the existing re-discovery checks cover the case (discovery
  still sees the device via `/v1/status`, and its entities already exist). The
  coordinator now tracks this state and raises a WARNING repair issue after 30 minutes,
  explaining the likely cause and remediation (check NTP/internet access, power-cycle
  the datalogger). The issue clears automatically — and the sensors recover on their
  own — as soon as the datalogger reports its data again. Localized in all
  10 languages. Only the datalogger is tracked: inverters legitimately drop out of
  livedata overnight.

- **Human-readable WiFi mode on the datalogger** — The "WiFi - Mode" sensor now shows
  "Station (Client)" instead of the raw code `1`, using the same state-map pattern as
  the Aurora status sensors (`WLAN_MODE_STATE_MAP` in `const.py`). Only value 1 is
  hardware-verified (fw 1.9.2 and 2.0.1 captures, logger connected as WiFi client);
  the AP-mode code is undocumented and unobservable in practice — a logger in AP mode
  is not on the LAN to be polled — so any other value renders as "Unknown (N)".

### Changed

- **Concrete self-service upgrade steps for VSN300 firmware 2.0.0 users** (Refs #68) —
  The repair issue, config-flow error, and README now give the hardware-confirmed
  upgrade procedure (datalogger web UI → FW UPDATE tab → Remote Update → Check for FW
  update → Download & Update) instead of the generic "contact FIMER support" guidance.
  Localized in all 10 languages. Procedure confirmed by @gseguin on real hardware.

### Documentation

- Corrected the v1.5.10 record after follow-up hardware testing by @gseguin (#68): the
  digest nc/cnonce constants are a robustness/alignment fix — stock RFC-style values are
  also accepted on all tested firmware, and the originally-reported 401s could not be
  reproduced. Also verified on hardware that the firmware stores user-entered text as
  genuine UTF-8, validating the UTF-8-first decode order of `read_json_lenient()`.

- Verified fw 2.0.1 on 3-phase hardware (Refs #68): the maintainer upgraded his VSN300
  (WIFI LOGGER CARD + PVI-10.0-OUTD 3-phase) from 1.9.2 to 2.0.1 with before/after
  captures — perfect parity on all endpoints (status 34 keys, inverter 52 points,
  datalogger 13 points, feeds 42 datastreams; zero added/removed, X-Digest web-UI
  constants accepted throughout). This was the last untested firmware/hardware
  combination in the #68 matrix. Sanitized reference captures added as
  `docs/vsn-data/vsn300-data/alexdelprete_vsn300_fw201_*`; upgrade UX caveat (a first
  "Download & Update" attempt can be a silent no-op — retry until the progress bar
  appears) recorded in the dev docs.

### Fixed

- **Diagnostics `sensor_summary` reported a single useless entry** — It iterated the
  top-level coordinator data keys instead of the per-device map, so every dump showed
  `"device_devices...": {"point_count": N}` (the device count mislabeled as a point
  count). It now lists one entry per device with `device_type`, `point_count`, and
  `has_points` — making a device that is present but not reporting (see the new repair
  issue above) immediately visible in a diagnostics dump.
